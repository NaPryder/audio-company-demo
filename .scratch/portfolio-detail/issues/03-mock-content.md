## Question

เขียนเนื้อหาจริงให้ครบทั้ง 6 โครงการตาม Q7 และ Q16:

- **เต็ม 2 ใบ** — `conference-room-av` (ระบบ AV สำหรับห้องประชุม) และ `auditorium-sound` (ระบบเสียงสำหรับหอประชุม)
- **สั้น 4 ใบ** — `meeting-presentation-system`, `training-room-sound`, `multipurpose-av`, `audio-control-system`

ต่อ 1 โครงการต้องได้:

1. `description` สำหรับ `data.ts` — คำโปรย 1 ประโยค (ถ้า ticket 02 ยืนยันว่ายังมี field นี้)

ข้อบังคับของเนื้อหา:

- **ไทยล้วน** น้ำเสียงเดียวกับ copy ที่มีอยู่แล้วใน `../../landing-page/spec.md` §12
- **ห้ามใส่ชื่อลูกค้า ชื่อสถานที่จริง ปี หรือตัวเลขที่ดูเหมือนของจริง** (Q8, Q11) — ของ mock ที่หน้าตาเหมือนของจริงคือสิ่งที่หลุดขึ้น production ได้ง่ายที่สุด
- **ห้ามอ้างยี่ห้ออุปกรณ์เจาะจง** — `Partner Brand` ใน `CONTEXT.md` ระบุว่าไม่ได้เป็นตัวแทนจำหน่ายอย่างเป็นทางการ

- ทุกใบต้องเขียนกำกับไว้ให้ชัดว่าเป็น mock — build session ต้องเห็นทันทีว่าอันไหนต้องเปลี่ยนก่อน deploy

**ผลลัพธ์ที่ต้องได้**: ข้อความครบ 6 ชุดอยู่ใน Answer ของ ticket นี้ พร้อมยกไปวางเป็นไฟล์ตอน build + gate 1 ข้อว่าต้องเปลี่ยนเป็นเนื้อหาจริงก่อน production.

## Answer

### วิธีทำเครื่องหมายว่าเป็น mock

ทุกไฟล์ขึ้นต้นด้วย HTML comment:

```md

ได้ผลสองชั้นพอดี: คนเปิดไฟล์เห็นทันทีบรรทัดแรก ส่วน `renderer.html` ที่ ticket 02 ตั้งไว้จะทิ้ง token
ประเภท `html` ทั้งหมด → **ไม่หลุดลงหน้าเว็บ**. ต่อให้ override นั้นพลาด สิ่งที่หลุดก็เป็นแค่ comment
ที่ผู้ใช้มองไม่เห็นอยู่ดี

### ตัวเลขและชื่อ

ไม่มีจำนวนอุปกรณ์ พื้นที่ ปี จำนวนที่นั่ง หรือชื่อสถานที่ในเนื้อหาเลยสักตัว — บรรยายองค์ประกอบระบบ
เชิงคุณภาพแทน. ตัวเลขที่แต่งขึ้นคือสิ่งที่แยกจากของจริงไม่ออกวันที่เนื้อหาจริงเข้ามาปนกัน

## ภาพรวมโครงการ

ห้องประชุมขนาดกลางที่เดิมใช้ลำโพงและไมโครโฟนแบบตั้งโต๊ะ ผู้เข้าร่วมที่นั่งปลายโต๊ะได้ยินไม่ชัด
และทุกครั้งที่มีผู้เข้าร่วมทางไกลต้องรอเจ้าหน้าที่มาตั้งค่าอุปกรณ์ให้ก่อนเริ่มประชุม

โจทย์ของงานนี้จึงไม่ใช่การเพิ่มกำลังขับ แต่เป็นการทำให้เสียงกระจายทั่วห้องอย่างสม่ำเสมอ
และย่อขั้นตอนก่อนเริ่มประชุมให้เหลือน้อยที่สุด
**คนที่เดินเข้ามาใช้ห้องต้องเริ่มประชุมได้เองโดยไม่ต้องเปิดคู่มือ**

## ข้อพิจารณาของพื้นที่

ผนังกระจกและเพดานเรียบทำให้เสียงสะท้อนค้างในห้องนานกว่าที่ควร
ตำแหน่งลำโพงและรูปแบบการกระจายเสียงจึงถูกกำหนดจากผังห้องจริงก่อน แล้วจึงเลือกอุปกรณ์ให้สอดคล้อง
ไม่ใช่ลำดับกลับกัน

ไมโครโฟนวางให้ครอบคลุมตำแหน่งที่นั่งที่ใช้งานจริง ไม่ใช่กระจายให้ทั่วโต๊ะเท่า ๆ กัน
เพราะการรับเสียงในบริเวณที่ไม่มีคนนั่งมีแต่จะดึงเสียงรบกวนเข้าระบบ

## ขอบเขตงาน

- สำรวจพื้นที่และประเมินลักษณะการสะท้อนเสียงของห้อง
- ออกแบบตำแหน่งลำโพงและไมโครโฟนจากผังที่นั่งจริง
- ติดตั้งจอแสดงผลและกล้องสำหรับการประชุมทางไกล
- เดินสายและติดตั้งตู้อุปกรณ์พร้อมการระบายความร้อน
- ตั้งค่าระบบประมวลผลเสียงและบันทึกค่าที่ใช้งานจริงไว้ให้ย้อนกลับได้
- จัดหน้าจอควบคุมให้เหลือเฉพาะปุ่มที่ผู้ใช้ทั่วไปต้องใช้
- ทดสอบร่วมกับผู้ใช้งานและอบรมการใช้งานเบื้องต้น
```

## แนวทางที่ใช้

แทนที่จะปรับทีละค่าหน้างาน ระบบถูกจัดเป็นชุดค่าที่บันทึกไว้ล่วงหน้าตามรูปแบบการใช้งาน
ผู้ดูแลเลือกจากรายการแล้วเริ่มงานได้เลย

1. ประเมินการตอบสนองของห้องก่อนออกแบบ
2. แบ่งโซนลำโพงตามระยะและระดับความสูงของที่นั่ง
3. บันทึกชุดค่าตามรูปแบบงานที่เกิดขึ้นจริง
4. ส่งมอบพร้อมเอกสารที่ผู้ดูแลกลับมาอ่านเองได้

ระบบเผื่อช่องต่อสำหรับอุปกรณ์ที่ผู้จัดงานนำมาเองไว้ด้วย
เพราะ *งานที่มาเช่าใช้พื้นที่มักมาพร้อมอุปกรณ์ของตัวเอง* และการต้องรื้อระบบหลักเพื่อรับอุปกรณ์ภายนอก
คือจุดที่ระบบเสียหายบ่อยที่สุด

## ขอบเขตงาน

- ประเมินการตอบสนองเสียงของห้องและกำหนดโซนลำโพง
- ติดตั้งลำโพงหลักและลำโพงเสริมสำหรับที่นั่งด้านหลัง
- ติดตั้งระบบมอนิเตอร์บนเวที
- วางระบบไมโครโฟนไร้สายและจัดช่วงความถี่ไม่ให้ชนกัน
- ติดตั้งชุดควบคุมที่ห้องควบคุมและจุดควบคุมสำรองข้างเวที
- บันทึกชุดค่าตามรูปแบบการใช้งานและทดสอบการสลับใช้งานจริง
- ส่งมอบเอกสารการใช้งานและอบรมผู้ดูแลประจำอาคาร

หากกำลังวางแผนงานลักษณะเดียวกัน [เล่าให้เราฟังเกี่ยวกับพื้นที่ของคุณ](/contact)
เพื่อให้ทีมงานช่วยประเมินแนวทางต่อไป
